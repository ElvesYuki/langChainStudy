# AGL-01-01：模型生命周期

目标深度：D1 了解  
当前学习状态：未开始 → 本轮只讲解，不更新学习记录

## 1. 本节目标

学完后，你应能准确解释：

- 预训练、监督微调、偏好对齐、强化学习分别解决什么问题。
- 为什么模型“知道很多”不等于“会按指令办事”。
- 偏好对齐与强化学习不是同义词。
- 推理模型与普通生成模型的主要差异。
- 这些训练阶段如何影响 PEF 的模型选型、延迟、稳定性和成本。

本节不要求掌握梯度下降、Transformer 数学推导、PPO/DPO 公式或训练集群实现。

---

## 2. 为什么需要这个能力

PEF 调用的是已经训练完成的外部模型，但你仍需理解模型怎么形成能力，因为 Runtime 遇到的许多问题都来自模型本身：

- 模型懂知识，却不一定听指令。
- 模型会生成 ToolCall，却不保证参数正确。
- 偏好对齐改善了行为，却不能保证事实正确。
- 推理模型复杂任务更强，但通常更慢、更贵。
- `temperature=0` 降低随机性，却不等于绝对确定。
- 模型安全训练不能代替 PEF 的权限、Secret 和项目隔离。

一句话概括：

> 训练决定模型大致“能做什么、倾向怎么做”；PEF Runtime 决定如何安全、可靠、可审计地使用这些能力。

## 3. 核心概念和术语

### 3.1 预训练 Pretraining

预训练的核心任务通常是：

> 给定前面的 Token，预测下一个 Token。

例如：

```text
输入：Java 中 HashMap 的底层结构是
目标：数组
```

模型在海量文本、代码等数据上反复进行这种预测，逐渐获得：

- 语言和代码模式。
- 世界知识的统计表示。
- 上下文关联能力。
- 一部分推理、归纳和模仿能力。

但预训练模型本质上擅长的是“续写”，不天然等于：

- 听从用户指令。
- 拒绝危险请求。
- 输出严格 JSON。
- 正确调用 Tool。
- 承认自己不知道。

OpenAI 对 InstructGPT 的说明也强调：单纯扩大预训练模型，并不会自然使其更符合用户意图；后训练更多是在引导和释放预训练中已经形成的能力。[OpenAI：Aligning language models to follow instructions](https://openai.com/index/instruction-following/)

### 3.2 监督微调 SFT

SFT 使用高质量的“输入 → 理想输出”示范训练模型。

```json
{
  "input": "请提取用户姓名和手机号",
  "ideal_output": {
    "name": "张三",
    "phone": "13800138000"
  }
}
```

它主要教模型：

- 如何遵循指令。
- 如何以对话助手的方式回答。
- 如何使用特定格式。
- 如何模仿 ToolCall、JSON、代码等输出模式。
- 特定领域任务应该怎样完成。

可以把它理解成给一个知识广泛但行为散乱的开发者提供“标准实现和金样”。

SFT 的局限是：

- 很难为所有输入编写唯一的完美答案。
- 容易学到示范数据的风格和偏差。
- 没见过的边界仍可能失败。
- 它不天然解决多个“都能接受”的答案之间如何排序。

### 3.3 偏好对齐 Preference Alignment

偏好数据通常不是告诉模型唯一正确答案，而是比较两个候选：

```json
{
  "prompt": "如何重置数据库？",
  "preferred": "先备份并确认环境，再执行受控迁移。",
  "rejected": "直接删除数据库重新创建。"
}
```

它主要学习：

- 哪个回答更有帮助。
- 哪个回答更安全。
- 哪个回答更符合风格要求。
- 哪个回答更诚实、简洁或稳健。

偏好对齐是一个目标类别，不等于 RLHF。实现方式可以包括：

- RLHF：训练奖励模型，再用强化学习优化语言模型。
- RLAIF：偏好主要由 AI 按规则评估。
- DPO 等直接偏好优化：直接使用偏好对更新模型，不必运行完整的奖励模型加在线强化学习流程。[DPO 论文](https://arxiv.org/abs/2305.18290)

所以正确关系是：

```text
偏好对齐
├── RLHF
├── RLAIF
├── DPO 类直接偏好优化
└── 其他后训练方法
```

### 3.4 强化学习 RL

强化学习的核心结构是：

```text
模型产生行为 → 环境或评分器给出奖励 → 优化产生高奖励行为的概率
```

在大模型领域，RL 至少有两类常见目标：

1. 行为对齐

   奖励来自人类偏好、AI 偏好或安全规则，目标是更有帮助、更安全、更符合指令。

2. 推理能力强化

   对数学答案、代码测试、证明结果等可验证任务给奖励，鼓励模型学习分解、检查和修正问题。

InstructGPT 的经典流程是 SFT、偏好排序、奖励模型、PPO 强化学习。[InstructGPT 论文](https://arxiv.org/abs/2203.02155)

但这不是所有现代模型的固定流水线。DeepSeek-R1 的公开研究显示，RL 可以明显强化推理行为；纯 RL 版本也暴露了可读性和语言混杂问题，因此正式 R1 又加入了冷启动数据和多阶段训练。[DeepSeek-R1 论文](https://arxiv.org/abs/2501.12948)

### 3.5 推理模型与普通生成模型

二者底层都在逐 Token 生成，区别主要在于是否被训练和配置为投入更多推理时计算。

| 维度 | 普通/直接生成模式 | 推理模式 |
|---|---|---|
| 典型任务 | 摘要、改写、分类、简单问答 | 数学、代码、规划、复杂约束 |
| 输出方式 | 较快形成答案 | 先进行更多内部推理再回答 |
| 延迟 | 通常较低 | 通常较高 |
| Token/计算量 | 较少 | 可能包含大量推理 Token |
| 成本 | 通常较低 | 通常较高 |
| 简单任务收益 | 通常足够 | 可能是过度计算 |
| 复杂任务稳定性 | 容易跳步 | 通常更擅长分解和检查 |

这不是绝对的模型二分法。当前模型越来越倾向于在同一模型家族内提供不同推理等级或模式。官方 API 也明确指出，降低 reasoning effort 可以减少推理 Token、提高速度；额外推理并非对所有任务都有收益。[OpenAI reasoning 参数说明](https://platform.openai.com/docs/api-reference/responses-streaming/response/reasoning_summary_part?lang=javascript)

因此更准确的说法是：

> “推理模型”是更偏重推理训练和推理时计算的生成模型，而不是完全不同的技术物种。

## 4. 底层协议或数据结构

D1 只需记住五种训练数据形态：

```text
预训练：
[token1, token2, token3] -> 预测 token4

SFT：
instruction + context -> ideal_response

偏好数据：
prompt + preferred_response + rejected_response

RL：
state + generated_action/response -> reward

推理时：
messages + tools + inference_budget -> answer/tool_calls
```

对应的能力来源可以粗略理解为：

```text
预训练     → 知识、语言、代码和基础能力
SFT        → 指令遵循和任务格式
偏好对齐   → 行为倾向、安全性和回答风格
推理强化   → 多步推导、检查和复杂问题能力
Runtime    → 权限、工具、状态、恢复与审计
```

## 5. 最小实现或伪代码

这不是实际训练代码，只表示生命周期：

```python
base_model = pretrain(corpus)

instruction_model = supervised_finetune(
    base_model,
    instruction_demonstrations,
)

aligned_model = preference_optimize(
    instruction_model,
    preference_pairs,
)

reasoning_model = reinforce(
    aligned_model,
    tasks_with_verifiable_rewards,
)

response = reasoning_model.generate(
    messages=messages,
    inference_budget="medium",
)
```

真实厂商流程可能交叉、重复、蒸馏，也可能不用其中某一步。

## 6. 常见框架如何实现

训练框架通常负责：

- Transformers：模型结构、加载和基础训练。
- DeepSpeed/FSDP：多卡、显存和分布式训练。
- TRL 等：SFT、奖励模型、DPO、PPO 等后训练。
- vLLM等推理引擎：部署训练完成的模型。

LangChain、LangGraph、Agent SDK 的角色不同：

> 它们主要编排已经训练好的模型，不负责让模型通过预训练获得知识，也不会自动完成生产级权限和可靠执行。

PEF 同样属于模型消费和 Agent Runtime 平台，不是基础模型训练平台。

## 8. PEF 真实调用链

```text
POST /conversation/chat
  → AiConversationService.prepare
      固定 project、user、session、main agent、release
  → AgentExecutionService.execute
      创建 Execution / Attempt，Claim Lease
  → AgentRuntime
      装配 Release、Context、Knowledge、Tool Schema
  → RuntimeLoop
      判断调用模型、执行工具或结束
  → ModelInvoker.invoke
      解析 Secret，记录 ProviderInvocation，处理取消和重试
  → ProviderRouter
  → LiteLLMProvider
  → 外部模型 Provider
  ← content / tool_calls / usage / stop reason
  → PEF ModelCallResult
  → Transcript / Stage / RequestLog / Execution 结算
  → Conversation Turn 投影
```

训练生命周期在这条链之前已经完成。PEF 接收到的是厂商发布的模型名称和推理协议，而不是模型训练数据或权重更新过程。

当前项目事实还体现了模型差异的真实影响：

- 主 Agent 的 DeepSeek 与 LongCat 候选经过多次真实评测，不能只凭模型宣传切换。
- `temperature=0.0` 仍出现过空文本和不稳定输出，说明零温度不等于业务确定性。
- LongCat 曾出现接近 197 秒的确定成功调用，说明复杂模型的长尾延迟会直接影响超时和恢复设计。
- PEF 明确不把 `reasoning/thinking` 内容作为最终回答写入 SSE、Transcript 或 RequestLog。

当前不足也要如实指出：

- PEF 已能识别并阻止 reasoning 内容被当作最终正文。
- 但通用 `ModelUsage` 目前主要记录 prompt、completion、total Token。
- `reasoning_effort`、独立 reasoning Token 和跨 Provider 推理预算尚未形成一等统一协议。
- 目前只有特定评测路径通过 `extra_body` 控制 DeepSeek Thinking。

这不一定是当前缺陷，因为生产主模型使用的是非 Thinking 配置；如果未来正式引入多种推理模型，应先定义跨 Provider 的推理预算、Usage、成本和输出契约，而不是仅增加一个前端开关。

## 9. 教学实现与生产实现的差异

| 层级 | 典型做法 |
|---|---|
| 教学 Demo | 选一个模型，发送 Prompt，打印回答 |
| 框架默认实现 | 封装消息、流式输出、ToolCall 和少量重试 |
| PEF 生产实现 | 固定 Release、项目隔离、Secret 末端解析、Execution/Attempt、取消、ProviderInvocation、unknown、Transcript、成本和发布评测 |

教学案例通常假设“模型调用成功就结束”。

PEF 必须继续回答：

- 调用是否真的发送出去了？
- 响应丢失后能否重试？
- 当前 Execution 是否仍持有 Lease？
- 模型和参数来自哪个不可变 Release？
- Secret 是否进入了日志？
- reasoning 内容是否被误当成最终答案？
- 这个模型是否通过了 Dataset 和 Promotion 门禁？

## 10. 失败场景

- 超时：推理模型更容易产生长尾延迟；超时后可能不知道 Provider 是否已完成。
- 取消：本地协程取消不等于 Provider 停止计算或停止计费。
- 并发：推理模型通常消耗更多 Token 和计算资源，更容易触发 RPM/TPM 或容量限制。
- 重复：同一 Prompt 多次调用可能得到不同结果；零温度也不构成幂等保证。
- 崩溃：发送请求后进程崩溃，必须通过 ProviderInvocation 和 Attempt 判断状态。
- unknown：请求可能已发送，但没有可信响应，不能盲目自动重放。
- 输出耗尽：推理消耗了预算，却没有留下足够 Token 生成最终答案。
- ToolCall 截断：复杂推理后输出的工具参数可能因 Token 上限被截断。

PEF 将这些问题放在 Runtime 和 Execution 层治理，而不是指望模型训练阶段自动解决。

## 11. 安全问题

需要牢牢记住：

> 模型对齐只影响行为概率，不授予任何业务权限。

即使模型经过安全训练：

- Prompt Injection 仍可能诱导它调用危险 Tool。
- 模型生成 ToolCall 不等于用户有 Tool 权限。
- 模型不能决定自己可以读取哪个项目的数据。
- API Key 不能因为模型“需要”就进入 Prompt。
- reasoning 内容可能包含敏感中间信息，不能默认持久化或展示。
- 外发给 Provider 的业务数据仍需独立的数据合规授权。

PEF 对应防线包括：

- 后端唯一授权入口。
- `project_id/user/agent/session/execution` 多维隔离。
- Secret 引用和 Provider 末端解析。
- Tool 白名单、Schema 和副作用治理。
- reasoning/thinking 不进入用户正文和核心审计载荷。
- 不可信知识与 ToolResult 不能提升权限。

## 12. 常见误区

1. “预训练就是把资料存进数据库。”

   错。它是通过优化参数学习统计模式，不是可精确查询的知识库。

2. “SFT 可以让模型永久记住企业文档。”

   不准确。企业动态知识通常更适合版本化 RAG；SFT 更适合改变行为和任务模式。

3. “偏好对齐就是 RLHF。”

   错。RLHF 只是偏好对齐的一种实现。

4. “推理模型不会幻觉。”

   错。它只是更可能进行多步检查，不代表事实必然正确。

5. “模型会调用 Tool，所以它具备 Agent 权限。”

   错。模型只有调用意图，权限属于平台。

6. “temperature=0 就完全确定。”

   错。Provider 实现、并行计算、模型版本和输出协议仍可能产生差异。

7. “参数量越大，指令遵循一定越好。”

   错。预训练规模和对齐质量是不同维度；InstructGPT 已展示较小的对齐模型在用户偏好上胜过大得多的基础模型。

## 13. 面试时如何表达

可以这样回答：

> 大模型通常先通过预训练获得语言、知识和基础推理能力，再通过 SFT 学习指令和任务示范，通过偏好对齐改善有用性、安全性和输出风格。偏好对齐不等于强化学习，RLHF、RLAIF、DPO 都可能服务于这一目标。推理模型本质上仍是生成模型，但通过训练和推理时计算预算强化多步推导，因此复杂任务质量通常更高，同时带来更大的延迟、Token 和成本。Agent 平台不能把模型对齐当成权限和可靠性保证，仍需独立治理 Tool、Secret、Execution、幂等、恢复和审计。
