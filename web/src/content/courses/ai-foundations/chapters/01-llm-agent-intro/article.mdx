## 先从一项真实工作任务开始

这次不把大模型讲成一组技术名词，也不把智能体讲成“更厉害的聊天机器人”。我们沿着一项可以检查的办公任务，看软件内部到底发生了什么。

<CaseStudy title="把两份材料变成一份可以验收的培训需求汇报">

- 输入一：`培训报名统计.xlsx`，共 128 条报名记录。
- 输入二：`需求访谈记录.docx`，包含 6 段跨部门访谈。
- 产物：不超过 5 页的培训需求汇报。
- 验收：人数合计等于 128；结论能够回到数据或原文；未知事实明确标记；建议和问题对应。

</CaseStudy>

这项任务里既有必须算准的数字，也有需要依据的归纳，还有需要业务判断的建议。它足够接近日常工作，也能把模型、工具、智能体和人的边界放在同一个画面里。

## 你打开的是 AI 应用，不是直接面对一个模型

WorkBuddy 一类软件首先是一个 **AI 应用**。它把界面、文件、模型、工具、权限和任务记录组合成用户能够操作的产品。

<ConceptCard label="AI APPLICATION" title="AI 应用负责把能力组合成可使用的软件" tone="blue">

大模型只是应用内部的一项能力。文件怎么进入系统、模型能看到什么、工具是否有权限、任务状态保存在哪里，都由应用和运行环境决定。

</ConceptCard>

因此，“软件能做什么”不能只看它连接了哪个模型。相同模型放进不同应用，可能拥有完全不同的文件能力、操作范围和安全边界。

## 上下文：模型这一次真正拿到的信息

把文件拖进软件，并不等于模型天然看到了文件内容。通常要先经过工具读取、格式解析和内容筛选，提取结果才会进入本次请求的上下文。

  rightTitle="工具读取之后"

  right={<ul><li>四部门人数合计 128</li><li>6 段访谈原文</li><li>材料外事实必须标记</li><li>汇报不超过 5 页</li></ul>}

<Callout title="一句话记忆">
模型能力决定“会不会做”，上下文决定“这一次根据什么做”。没有进入上下文的公司内部事实，模型就不知道。
</Callout>

## 上下文不是越多越好

上下文不是一个无限容量的资料仓库。实际软件通常需要在相关性、容量和安全之间做选择：

- **相关性**：分析培训需求时，不需要把整个公司云盘都提供给模型；
- **容量与注意力**：长文件需要分段、筛选和检索，无关内容过多会稀释重点；
- **安全与权限**：工具能够读取某份文件，不代表所有内容都应该进入模型输入；
- **可追溯性**：重要结论最好能够定位到具体工具结果或原文片段。

<Callout type="warning" title="上下文的边界">
好的上下文不是“尽可能多”，而是与当前目标相关、信息充分、来源可追溯，并且经过授权。
</Callout>

## 大模型：接收当前输入，再逐步生成输出

从最基础的角度理解，大模型做的是一件事：**接收输入，根据训练形成的能力，逐步生成输出。**

本次任务的输入可能包含目标、报名统计、访谈片段和验收规则。模型根据这些输入，可以生成：

- 一段培训需求总结；
- 一个结构化的部门统计结果；
- 一份五页汇报的页面结构；
- 下一步应该调用哪个工具的意图；
- 材料不足时需要向人确认的问题。

<ConceptCard label="MODEL" title="模型输出的不只是自然语言" tone="violet">

输出可以是文字，也可以是 JSON、表格结构、分类结果或工具调用意图。但无论形式多规整，它仍然是模型生成的结果，可能遗漏、误解或产生没有依据的内容。

</ConceptCard>

模型不会自动进入公司的数据库查找固定答案，也不会因为“听起来确定”就变成事实。判断输出是否可信，需要检查它能否回到当前材料和真实执行结果。

## 大模型擅长什么，又缺少什么

大模型擅长处理语言和模式，例如改写、归纳、分类、提取、生成大纲和形成结构化草稿。但下面四种能力不能混在一起：

| 问题 | 大模型本身 | 还需要什么 |
| --- | --- | --- |
| 能否归纳 6 段访谈 | 可以根据输入生成归纳 | 检查结论是否能回到原文 |
| 是否知道公司内部报名数据 | 默认不知道 | 工具读取并放入上下文 |
| 能否精确统计 128 条记录 | 可以尝试推理，但不应依赖猜测 | 表格工具或程序执行计算 |
| 建议是否适合公司执行 | 可以生成建议 | 业务人员判断、授权和验收 |

<Callout title="能力不等于事实和行动">
“模型能生成”不等于“它知道内部事实、拥有系统权限、已经执行动作或能够承担业务责任”。
</Callout>

## 工具：真正读取、计算、写入和执行

模型可以生成“读取报名表并按部门计数”的调用意图，但真正打开文件、统计数据的是工具。

工具可以用四个基础动作理解：

- **读**：读取文件、数据库、网页或系统状态；
- **写**：创建文档、表格、邮件草稿或代码；
- **改**：修改已有内容；
- **执行**：运行计算、脚本、检查或外部操作。

复杂工具，本质上往往是这些基础动作的组合和封装。

<ProcessFlow steps={[
  { title: "模型提出意图", description: "调用 analyze_spreadsheet，读取报名表并按部门计数。" },
  { title: "应用检查", description: "检查工具是否存在、文件是否允许访问、参数是否合法。" },
  { title: "工具执行", description: "真正读取文件并完成统计，而不是由模型凭空计算。" },
  { title: "结果返回", description: "返回四部门人数、合计值、执行状态或错误信息。" },
]}/>

一次具体调用可能表达为：

```text
tool: analyze_spreadsheet
file: 培训报名统计.xlsx
operation: group_count
group_by: 部门
```

平台检查工具、文件权限和参数后，才真正执行。成功结果可能是：

```text
status: success
研发: 46    运营: 31
行政: 27    产品: 24
total: 128
```

如果返回 `permission_denied` 或 `field_not_found`，智能体看到的是失败结果，必须等待授权、修改参数或请求人工接管，而不能把调用意图当成成功结果。

<Callout type="warning" title="四件事不能画等号">
模型提出调用意图，不等于已经获得权限；获得权限不等于执行成功；执行成功也不等于业务结果一定正确。
</Callout>

## 智能体：围绕目标持续推进任务

如果只有一次模型调用，软件往往只能完成“输入一次、回答一次”。智能体增加的是一个围绕目标持续推进的运行机制。

它通常要维护这些状态：

- 目标是什么；
- 哪些步骤已经完成；
- 当前正在处理什么；
- 工具返回了什么；
- 后面还有哪些步骤；
- 哪些信息缺失，需要停止并询问。

<ConceptCard label="AGENT" title="智能体不是另一种大模型" tone="green">

智能体把模型、工具、上下文和任务状态组织成循环：理解当前状态，决定下一步，执行工具，观察结果，再决定继续、重试、停止或请求人工确认。

</ConceptCard>

在贯穿案例里，智能体可以先读取报名表，再读取访谈，随后生成汇报，最后检查人数、依据和页数。如果访谈缺少来源部门，它不应该擅自补齐，而应该把问题放进“待确认”状态。

## 智能体循环怎样推进

智能体通常通过一个反复更新的循环工作：

1. **判断下一步**：根据目标、当前状态和已有结果，决定现在最需要做什么；
2. **调用工具**：读取访谈、统计数据、生成文件或执行检查；
3. **观察结果**：成功、失败、权限拒绝和字段缺失都会影响下一步；
4. **更新状态**：记录已完成、当前、待完成和待确认；
5. **决定去向**：继续、重试、停止、请求人工确认，或者满足验收后交付。

这个循环不是无限执行。可靠的智能体还需要：停止条件、重试上限、超时处理、权限控制和人工接管点。

<Callout type="warning" title="规划不是一次完成的">
工具每次返回的新结果，都可能让原计划失效。智能体需要根据真实结果调整，而不是机械执行最初生成的步骤清单。
</Callout>

## AI 应用、大模型和智能体是什么关系

这三个概念不在同一层：

- **大模型**是一种生成与判断能力；
- **智能体**是一种围绕目标组织模型、工具和状态的运行机制；
- **AI 应用**是用户实际使用的软件产品，它可以只提供普通对话，也可以在内部运行一个或多个智能体。

所以，一个 AI 应用不一定是智能体；一个智能体通常要运行在某个应用或平台中；智能体也不等于它调用的大模型。

## 把概念连成一条完整任务链

回到培训需求分析案例，软件可以留下这样一条可追溯链路：

1. **应用接收**：目标、两份文件和四项验收条件；
2. **工具读取**：表格工具返回四部门人数，文档工具返回 6 段访谈及来源；
3. **上下文组织**：把目标、工具结果、相关原文、规则和当前状态交给模型；
4. **模型生成**：形成关注问题、对应依据、培训建议、页面结构和待确认项；
5. **智能体推进**：检查数字、依据与页数，根据异常继续、重试、停止或询问；
6. **人工验收**：确认材料授权、数字准确、结论有依据，并判断建议是否适合执行。

这条链路最重要的不是步骤数量，而是每一步都有输入、动作、返回结果、当前状态和验收依据。

## 最重要的职责边界

<BoundaryTable />

可以把最终边界压缩成一句话：

> 模型负责生成，工具负责执行，智能体负责推进，人负责目标、授权和验收。

## 为什么一定需要人接管

智能体能够自动推进，并不意味着它应该无限重试或替人做业务决定。以下情况都应该停下来：

1. 128 条报名记录中有 3 条部门为空，现有部门合计只能得到 125；
2. 工具返回 `permission_denied`，软件没有读取材料的权限；
3. 汇报声称“财务最关注安全”，但材料里根本没有财务数据；
4. PPT 已经生成，但其中一条建议没有数据或访谈依据；
5. 系统需要发送邮件、覆盖文件或提交审批，而用户尚未授权。

可靠的软件应该允许观察、停止、补充材料、修改参数、重试和人工接管，而不是只展示一个看起来完整的最终答案。

## 怎样给智能软件一份完整任务说明

<Comparison
  leftTitle="信息不足"
  rightTitle="任务定义清楚"
  left={<div><p>“帮我做一份培训需求分析。”</p><ul><li>没有真实材料</li><li>没有说明最终产物</li><li>没有权限边界</li><li>没有验收标准</li></ul></div>}
  right={<div><p>“基于报名表和访谈记录，生成不超过 5 页的培训需求汇报。”</p><ul><li>统计四部门人数</li><li>结论必须有数据或原文</li><li>材料外事实标记待确认</li><li>数字和结论能够追溯</li></ul></div>}
/>

复杂任务需要说明五件事：

1. **目标**：真正要解决什么问题；
2. **上下文**：依据哪些材料、规则和历史信息；
3. **工具权限**：允许读取、修改或执行什么；
4. **产物**：最终交付什么格式和范围；
5. **验收标准**：怎样判断任务真的完成。

这不是寻找一句“神奇提示词”，而是在给软件一份结构完整、可以检查的任务说明。

## 一个实用方法：先转换成适合分析的中间表示

复杂任务里，我通常不会让 AI 直接围绕最终版 Word 或 Excel 反复修改，而是先保留原始文件，再建立一份更适合分析的工作副本：

1. **保留原件**：Word、Excel、PDF 继续作为格式、数据和验收依据；
2. **转换工作副本**：叙述性内容转成 Markdown，表格数据保留为 Excel，或导出为 CSV、JSON；
3. **分别处理**：AI 负责归纳、比较和写作，表格工具或程序负责精确计算；
4. **组织中间结果**：把结论、依据、待确认项整理成 Markdown 或 JSON；
5. **生成业务产物**：根据使用场景生成 Word、Excel 或 PPT；
6. **回到原件验收**：核对数字、公式、原文依据和最终版式。

<Callout title="关键不是全部转成 Markdown">
不同材料应该选择不同的中间表示：文字适合 Markdown，精确表格适合 CSV、JSON 或 Excel，图片和复杂版式需要保留原始文件。Markdown 是分析工作副本，不是新的权威事实源。
</Callout>

| 原始材料 | 建议的分析形式 | 需要保留的原始信息 |
| --- | --- | --- |
| 需求、访谈、制度等文字 | Markdown | 标题层级、原文位置、批注和修订 |
| 报名明细、预算、交易记录 | CSV、JSON 或 Excel | 字段类型、公式、多工作表关系和统计口径 |
| 图片、扫描件、复杂 PDF | OCR 文字 + 原始文件 | 图片、页码、阅读顺序和版式关系 |
| 阶段性分析结果 | Markdown 或 JSON | 来源引用、假设、待确认项和生成时间 |

例如，可以为一项任务准备这样的工作目录：

```text
培训需求分析/
├── originals/                 # 原始 Word、Excel，只作为依据使用
├── context.md                 # 目标、范围、规则和验收标准
├── interviews.md              # 访谈文字与来源定位
├── registrations.csv          # 报名明细
├── analysis.md                # 结论、依据和待确认项
└── outputs/                   # 最终 Word、Excel 或 PPT
```

这种方式在材料多、需要反复分析、需要生成多种产物或要求结论可追溯时，通常更稳定、更容易复用。如果只修改一份很短的文档，额外转换反而可能降低效率。

<Callout type="warning" title="转换也可能丢失信息">
Word 转 Markdown 可能丢失批注、修订和复杂排版；Excel 转 Markdown 可能丢失公式、数据类型、多工作表关系和隐藏信息。转换完成后必须记录来源，并用原始文件做最终核对。
</Callout>

## 放回不同部门的工作中

虽然材料和工具不同，但任务结构基本一致：

| 部门 | 常见材料 | 可能产物 | 重点验收 |
| --- | --- | --- | --- |
| 行政 / 人事 | 名单、制度、模板 | 汇总、通知、待确认项 | 人员与制度准确 |
| 市场 / 运营 | 活动数据、用户反馈 | 复盘、问题归纳、建议 | 数据口径与依据 |
| 产品 | 访谈、需求池、历史版本 | 需求分类、冲突点 | 原意和优先级 |
| 财务 | 费用明细、预算规则 | 异常清单、核查结果 | 数字必须复核 |
| 研发 | 代码、日志、接口说明 | 定位建议、修改方案 | 测试与影响范围 |
| 管理者 | 周报、纪要、计划 | 项目摘要、风险和决策项 | 信息是否完整 |

识别一个任务是否适合交给智能软件，可以先找五件事：**材料、动作、产物、权限和验收标准。**

## 最后检查一下

下面三个说法都是错误的：

1. “WorkBuddy 就是一个大模型。”——它是组合界面、模型、数据、工具、权限和记录的 AI 应用。
2. “模型提出调用工具，就已经拥有权限。”——模型生成的是调用意图，实际权限由应用和运行环境决定。
3. “PPT 已经生成，所以任务完成了。”——文件存在只说明动作发生，业务结果还需要按材料和标准验收。

<Callout title="本章结论">
看懂智能软件，不要只看最终回答。要沿着任务检查：模型收到了什么、工具执行了什么、智能体保存了什么状态，以及最后由谁负责验收。
</Callout>

最后可以用五句话重新记忆：

1. 大模型是能力引擎，根据当前输入逐步生成输出；
2. 上下文决定模型这一次真正能够看到什么；
3. 工具让生成走向读取、计算和实际行动；
4. 状态与循环让智能体能够持续推进、停止和接管；
5. 人负责目标、材料授权和最终业务验收。
